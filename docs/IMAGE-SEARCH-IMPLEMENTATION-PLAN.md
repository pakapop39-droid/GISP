## ผลลัพธ์ที่ต้องการ

สมาชิกถ่ายภาพหรือเลือกรูปสินค้า แล้ว GISP แสดงสินค้าที่มีภาพเหมือนหรือคล้ายใน Catalog
เรียงจากใกล้เคียงที่สุด พร้อมเปิดรายละเอียดสินค้าได้ หากยังไม่พบสินค้าที่ต้องการ
สามารถไปส่งคำขอให้ทีมช่วยจัดหาผ่าน Slice 13 เดิมได้

## สิ่งที่ตรวจพบจากโครงการ

- `src/components/member-catalog-workspace.tsx` มีช่องค้นหาข้อความ หมวดสินค้า และรายการสินค้า พร้อมจุดเชื่อมไป Sourcing
- `src/app/api/member/catalog/route.ts` อ่าน `member_catalog` และค้นหาข้อความจากข้อมูลไม่เกิน 1,000 แถวในหน่วยความจำ จึงไม่ควรนำข้อจำกัดนี้มาใช้กับการค้นหาภาพ
- รูป Catalog อ้างอิงผ่าน `product_media` และ `file_metadata` เก็บใน Private Storage `gisp-confidential`
- `src/lib/catalog/member-server.ts` สร้าง Signed URL อายุ 300 วินาทีสำหรับแสดงรูป
- `src/lib/catalog/member-safe.ts` มีตัวแปลงข้อมูลเพื่อป้องกันข้อมูลโรงงานและต้นทุนหลุดไปยังสมาชิก
- `src/lib/files/image-upload.ts` มีการตรวจลายเซ็นไฟล์ JPEG, PNG และ WebP ที่นำมาใช้ต่อได้
- Slice 13 รองรับการแนบภาพและให้เจ้าหน้าที่จัดหาสินค้า ยังไม่มีโค้ดค้นหาภาพอัตโนมัติจากที่สำรวจ
- หลักฐาน `docs/evidence/2026-09-08-slice-13-visual-sourcing.md` ระบุว่า Slice 13 ยังเหลือ Human UAT และ Owner Sign-off 1 ขั้นตอน งานนี้ไม่เปลี่ยนสถานะดังกล่าว

การสำรวจรอบวางแผนอ่านเฉพาะโค้ดและเอกสาร ต่อมาในขั้นตอนที่ 1 ตรวจ Development จริงแล้ว:
634 สินค้าที่ผ่านเงื่อนไข Catalog มีรูป 3,568 รายการ, decode ตัวอย่าง 727 ไฟล์ผ่าน,
และติดตั้ง pgvector 0.7.4 แล้ว ทดสอบ CLIP สองแบบบนเครื่องด้วย 97 คำค้นจาก 50 สินค้า
ต่อมาเชื่อม key เดิมจาก InsForge Model Gateway และทดลอง Voyage ผ่าน OpenRouter แล้ว
เลือก Voyage 1,024 dimensions สำหรับรุ่นทดลองต่อ; ยังขาดชุดภาพถ่ายจริง/คำตอบจากผู้ตรวจ
ดู [ผล baseline](evidence/2026-09-08-image-search-step1.md) และ
[ผล hosted ล่าสุด](evidence/2026-09-08-image-search-hosted-comparison.md) สำหรับตัวเลขและข้อจำกัด

## ขอบเขตรุ่นแรกที่เสนอ

- เริ่มจากสมาชิกที่เข้าสู่ระบบและมีสิทธิ์ใช้งานในหน้า `/member/catalog`
- ค้นหาครั้งละ 1 ภาพ รองรับ JPEG, PNG และ WebP; เสนอเพดานไฟล์ต้นฉบับ 10 MB
  โดยต้องทดสอบข้อจำกัด request ของ hosting และย่อภาพก่อนส่ง หากต้องรับไฟล์ใหญ่ใช้ private upload flow
- แสดงภาพตัวอย่าง เปลี่ยน/ล้างรูป และเลือกหมวดสินค้าได้
- แสดงผลสูงสุด 24 สินค้าไม่ซ้ำ เรียงตามความใกล้เคียง พร้อมรูป ชื่อ รหัส และข้อมูลสมาชิกตาม Catalog เดิม
- แสดงว่าเป็นผลใกล้เคียงจากภาพ ไม่กล่าวอ้างว่าเป็นรุ่นเดียวกัน และไม่แสดงคะแนนเป็นเปอร์เซ็นต์ความถูกต้อง
- สินค้าที่ไม่มีรูปยังค้นหาด้วยข้อความได้ แต่ไม่อยู่ในชุดค้นหาจากภาพ
- ยังไม่ขยายไป Public Shared Catalog, การค้นหาบนอินเทอร์เน็ต, OCR, หลายภาพต่อคำค้น หรือการฝึกโมเดลใหม่
- เก็บรูปสินค้าหลายมุมที่มีอยู่เพื่อเปรียบเทียบได้ แต่ไม่ดึงภาพคำขอส่วนตัวของสมาชิกมาเป็น Catalog อัตโนมัติ

## ประสบการณ์ใช้งาน

1. กด “ค้นหาด้วยรูปภาพ” ข้างช่องค้นหาเดิม แล้วเลือกไฟล์หรือถ่ายภาพบนมือถือที่รองรับ
2. เห็นตัวอย่างรูปและคำแนะนำให้เน้นสินค้าหนึ่งชิ้น จากนั้นกดค้นหา
3. ระหว่างประมวลผลแสดงสถานะและป้องกันการส่งซ้ำ; เมื่อเปลี่ยนรูปต้องไม่แสดงผลเก่าทับผลใหม่
4. แสดงผลสินค้าที่คล้ายกัน เลือกหมวดเพื่อกรองได้ ในโหมดนี้ใช้การเรียงตามความใกล้เคียง
5. เปิดรายละเอียดสินค้าเดิม หรือล้างรูปเพื่อกลับไปค้นหาข้อความ
6. เมื่อไม่พบผลที่ใกล้เคียงพอ แนะนำเปลี่ยนรูป/หมวด และแสดงปุ่มส่งภาพให้ช่วยจัดหาเมื่อ Sourcing เปิดใช้งาน
   รุ่นแรกเปิดแบบฟอร์มเดิมให้สมาชิกแนบรูปและกดส่งเอง ไม่สร้างหรือส่งคำขอโดยอัตโนมัติ

แยกข้อความระหว่าง “ไม่พบสินค้าที่ใกล้เคียง”, “กำลังเตรียมภาพสินค้า” และ “ค้นหาไม่สำเร็จ ลองใหม่”
เพื่อไม่ให้บริการ AI ล่มถูกตีความว่าไม่มีสินค้า

## แนวทางระบบ

ใช้โมเดลที่รับภาพโดยตรงเพื่อแปลงภาพเป็นชุดตัวเลขสำหรับเปรียบเทียบ (image embedding)
รูปสินค้าและรูปค้นหาต้องใช้โมเดล รุ่น และวิธีเตรียมภาพเดียวกัน แล้วค้นหาด้วยระยะห่างของข้อมูลดังกล่าว
ใน Postgres ผ่าน pgvector ซึ่งเอกสาร InsForge ระบุว่ารองรับ

เลือกโมเดลหลังทดลองจริง โดยใช้โมเดลกลุ่ม CLIP เป็นตัวตั้งต้นสำหรับเปรียบเทียบ
และเปรียบเทียบบริการ image embedding ที่ตรวจสอบแล้วว่ารับภาพได้จริงอีกหนึ่งทางเลือก
ไม่ใช้ text-only embedding รับไฟล์ภาพ และไม่ถือว่าการบรรยายภาพแล้วค้นหาข้อความเทียบเท่าการเทียบภาพโดยตรง
เลือก Voyage multimodal 3.5 ตามการยืนยันของผู้ใช้แล้ว ดูผลเปรียบเทียบและขอบเขตค่าใช้จ่ายในหลักฐาน hosted

### เตรียมข้อมูลรูปสินค้า

- เสนอตาราง `product_image_embeddings`: อ้างอิง product/media/file, content hash,
  model/version, preprocessing version, vector, สถานะ และเวลาประมวลผล
- เสนอตารางงาน `product_image_index_jobs` เพื่อประมวลผลเบื้องหลัง มี retry จำกัดและเหตุผลที่ล้มเหลว
- กำหนด dimension หลังเลือกโมเดล และแยกข้อมูลต่างรุ่นเพื่อไม่เปรียบเทียบ vector คนละชนิด
- สร้างข้อมูลครั้งแรกเป็นชุดเล็กที่ทำต่อจากจุดเดิมได้ ไม่คำนวณภาพสินค้าทั้งหมดใหม่ทุกครั้งที่สมาชิกค้นหา
- เพิ่ม/เปลี่ยน/ลบรูปต้องสร้างหรือยกเลิกงานตาม lifecycle; งานเก่าต้องไม่เขียนทับรูปที่เปลี่ยนไปแล้ว
- ภาพหลายมุมให้รวมผลเป็นสินค้าเดียว โดยเริ่มทดลองจากคะแนนภาพที่ใกล้ที่สุด และตรวจผลลำเอียงต่อสินค้าที่มีรูปมาก
- แสดงรายงานพร้อมค้นหา/รอประมวลผล/ล้มเหลว/ไม่มีภาพ ให้เจ้าหน้าที่แก้เฉพาะรายการและสั่ง retry ได้

### การค้นหา

- เสนอ `POST /api/member/catalog/image-search` รับภาพและหมวดที่เลือก โดยตรวจสิทธิ์สมาชิกก่อนประมวลผล
- Backend ตรวจขนาดไฟล์จริง ลายเซ็น การ decode และเพดานจำนวนพิกเซล; ย่อภาพ แก้ทิศทางและลบ metadata ที่ไม่จำเป็น
- Backend สร้าง query embedding แล้วเรียก RPC ค้นหาในฐานข้อมูล ไม่โหลด vector ทั้งหมดไป browser
- กรองสิทธิ์และ eligibility ตาม `member_catalog` รวมสถานะเผยแพร่และราคาที่มีผล ก่อนเลือกผลอันดับแรก
  ต้องตรวจ eligibility ซ้ำตอนส่งผล เพื่อรองรับสินค้าถูกถอนระหว่างค้นหา
- กรองหมวดและรวมสินค้าซ้ำก่อนตัดจำนวนผล พร้อมทดสอบว่า vector index ไม่ทำให้ผลหายหลังกรอง
- ใช้ member-safe serializer เดิม และสร้าง Signed URL เฉพาะรูปผลลัพธ์ที่ผ่านสิทธิ์แล้ว
- ปรับ threshold จากชุดทดสอบ; หากไม่มีผลผ่านเกณฑ์ให้คืนผลว่าง ไม่เติมสินค้าที่ห่างไกลให้ครบ 24 รายการ
- งาน background ใช้สิทธิ์ server เท่าที่จำเป็น; สมาชิกเข้าถึง vector/jobs หรือสั่งประมวลผลสินค้าทั้งคลังตรง ๆ ไม่ได้

### การจัดเก็บและค่าใช้จ่าย

- ประมวลผลภาพค้นหาชั่วคราว; ถ้าจำเป็นต้องพักไฟล์ให้เก็บ private แยกจากรูปสินค้า ผูกเจ้าของ และลบภายใน 24 ชั่วโมง
  ต้องมี cleanup retry สำหรับงานที่ล้มเหลว ไม่เก็บภาพดิบหรือ signed URL ใน log
- เก็บเฉพาะข้อมูลวัดจำนวนคำค้น ระยะเวลา ผลสำเร็จ และค่าใช้จ่ายที่จำเป็น ไม่เก็บประวัติภาพค้นหาระยะยาวในรุ่นแรก
- ตรวจเงื่อนไขการเก็บภาพของผู้ให้บริการที่เลือกก่อนเปิดใช้ และบอกผู้ใช้ว่าภาพจะถูกประมวลผลเพื่อค้นหา
- กำหนด rate limit ต่อสมาชิก/บริษัท และจำนวนงานพร้อมกัน พร้อม quota รวมและ timeout
- ประเมินต้นทุนจาก (จำนวนรูปที่ต้องทำดัชนี × ราคาต่อรูป) + (คำค้นต่อเดือน × ราคาต่อคำค้น)
  + ค่ารัน worker/พื้นที่เก็บ/index; รายงานตัวเลขจริงหลังทดลอง ไม่ประมาณค่าบริการโดยไม่มีข้อมูล
- ตรวจ hosting timeout, payload size และงาน background ก่อนเลือกระหว่างบริการ API กับ worker แยก
- เปิดด้วย feature flag ทั้ง server และหน้าเว็บ เมื่อปิดแล้วต้องใช้ Catalog เดิมได้ตามปกติ

## แผนดำเนินงาน — เหลือ 4 ขั้นตอนหลัก

### 1. ทดลองความแม่นยำและสรุปต้นทุน

สำรวจจำนวนรูปจริงและความครบถ้วนต่อหมวด ตรวจความพร้อม pgvector และ runtime
เลือกชุดตัวอย่างอย่างน้อย 50 สินค้าหลายหมวด หรือทั้งหมดหากมีน้อยกว่า พร้อมภาพถ่ายต่างมุม/พื้นหลัง
ทำคำค้นอย่างน้อย 60 ภาพ: ภาพซ้ำหรือดัดแปลง 20, ต่างมุม/คล้าย 20, ไม่มีสินค้าตรงหรือภาพรบกวน 20
แยกชุดปรับเกณฑ์และชุดวัดผลโดยไม่ใช้ภาพเดียวกันซ้ำ เจ้าหน้าที่ระบุรายการที่ถือว่ายอมรับได้ล่วงหน้า

ผลส่งมอบ: รายงานคุณภาพรูป ผลเทียบทางเลือก โมเดลและ dimension ที่เลือก ค่าใช้จ่าย/ความเร็วที่วัดได้
พร้อมข้อจำกัด หากข้อมูลไม่พอให้รายงานและเติมชุดทดสอบก่อนถือว่าผ่าน

### 2. สร้างดัชนีภาพและระบบค้นหาฝั่งหลังบ้าน

สร้าง migration/RLS/RPC และ worker บน Development branch แยก
ทำ initial indexing, retry, sync เพิ่ม/เปลี่ยน/ลบรูป และ API ค้นหา พร้อมการตรวจสิทธิ์และ quota
ตรวจผลกับสินค้ามากกว่า 1,000 รายการเพื่อไม่รับข้อจำกัด loader เดิมเข้ามา

ผลส่งมอบ: ค้นหาภาพผ่าน API ได้จริง มีรายงาน coverage และตรวจ lifecycle/สิทธิ์ผ่าน

### 3. เพิ่มหน้าค้นหาภาพและทดสอบครบเส้นทาง

เพิ่มปุ่ม แนบ/ถ่ายภาพ ตัวอย่างรูป ผลใกล้เคียง ตัวกรอง ล้างรูป สถานะผิดพลาด และทางไป Sourcing
ทดสอบมือถือ/คอมพิวเตอร์ การเปิดรายละเอียด และการสลับกลับค้นหาข้อความ
ตรวจกรณีบริการช้า ล่ม ไฟล์ผิดชนิด รูปใหญ่ รูปเสีย quota เต็ม และการเปลี่ยนรูปขณะกำลังค้นหา

ผลส่งมอบ: Development Preview พร้อมหลักฐานการทดสอบ API และ browser

### 4. ให้ผู้ใช้ลองจริงและปิดงานบน Development

ให้เจ้าของงานทดลองสินค้าจริง ตรวจคุณภาพและค่าใช้จ่าย ยืนยันผล UAT
เตรียม backup/dry-run/merge ตาม workflow โครงการ ทดสอบหลัง deploy และบันทึก sign-off
ตรวจว่า feature flag ปิดฟีเจอร์และกลับไปใช้ Catalog เดิมได้
การเปิด Production จัดอยู่ในแผน release ของโครงการ ไม่ถือว่าเสร็จหรืออนุมัติแล้วจากเอกสารนี้

ผลส่งมอบ: รายงาน UAT, การยอมรับคุณภาพ, คู่มือสั้น, วิธีปิดฟีเจอร์ และหลักฐาน Development acceptance

## เกณฑ์รับงานที่เสนอ

ตัวเลขด้านคุณภาพและความเร็วเป็นเป้าหมายทดสอบ ไม่ใช่ผลที่ทำได้แล้ว
หากการทดลองไม่ผ่านให้ปรับวิธีหรือขอบเขตและบันทึกเหตุผลก่อนพัฒนาส่วนถัดไป

| รายการ | เป้าหมาย |
| --- | --- |
| ภาพซ้ำ/ย่อ/บีบอัดของสินค้าที่มีในระบบ | พบสินค้านั้นใน 5 อันดับแรกอย่างน้อย 95% ของชุดวัดผล |
| ภาพต่างมุมหรือสินค้าที่คล้าย | มีอย่างน้อย 1 ผลที่ผู้ตรวจยอมรับใน 10 อันดับแรก อย่างน้อย 80% ของชุดวัดผล |
| ภาพที่ไม่มีสินค้าคล้ายตามผู้ตรวจ | ไม่แสดงผลผ่าน threshold อย่างน้อย 90% ของชุดวัดผล |
| ความเร็ว | p95 ไม่เกิน 8 วินาทีหลังอัปโหลดเสร็จ บนขนาด Catalog จริงและผู้ค้นหาพร้อมกัน 5 คน; รายงาน cold start แยก |
| ความพร้อมรูป | รูปที่อยู่ในขอบเขตและ decode ได้มีดัชนีครบ 100%; รูปที่ใช้ไม่ได้มีรายการเหตุผล |
| สิทธิ์ | สินค้าซ่อน/เลิกเผยแพร่/ไม่มีสิทธิ์ และข้อมูลต้นทุน/โรงงานไม่ปรากฏในผลหรือ URL |
| อายุข้อมูล | เพิ่ม/เปลี่ยนรูปสะท้อนในดัชนีภายใน 5 นาทีภายใต้ภาระทดสอบ; ถอนสินค้าหรือลบรูปแล้วไม่แสดงข้อมูลที่หมดสิทธิ์ทันที |
| การดูแล | retry ได้โดยไม่เกิดรายการซ้ำ และ cleanup ภาพชั่วคราวผ่านกรณีงานล้มเหลว |
| ระบบเดิม | การค้นหาข้อความ รายละเอียดสินค้า และการส่งคำขอ Sourcing ยังทำงาน |

ตรวจ typecheck, lint, unit/integration tests ที่เกี่ยวข้อง, production build และ browser UAT
ระบุผล benchmark เป็นจำนวนที่ผ่าน/จำนวนทั้งหมดควบคู่กับเปอร์เซ็นต์ เพื่อให้เห็นขนาดหลักฐาน
