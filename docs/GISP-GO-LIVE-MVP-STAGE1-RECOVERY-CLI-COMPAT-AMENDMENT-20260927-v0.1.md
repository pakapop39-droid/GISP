## Why the exact old Recovery executor cannot pass

- The approved `reconcile.sql` SHA-256 `72CD3A7B96BA62B7E81293D172E0089CAD5E1B0FB5ED0F9DB6FB773D20898C2E` counts `public.payment_workflow_holds`. Read-only `to_regclass` on exact Staging Project `a24aff68-a82e-41da-b64a-a128a1539769` proves that table is absent; its Full Flow financial-controls Migration is intentionally deferred by Lean Scope. The other referenced application tables and private verifier exist. Missing is **not** the same as a count of zero.
- A read-only CLI probe on this Staging showed that multiple `SELECT` statements in one `db query` return `{"rows":[]}` even with exit code 0. The pinned single-call `run-reconcile.mjs` therefore cannot supply the individual count and ACL evidence required for Recovery.
- The CLI rejects a SQL argument beginning with a full-line `--` comment as an unknown option. Pinned Emergency Stop/Resume files begin with comments. Their SQL statements and file bytes must remain unchanged on disk; the transport needs a verified, comment-free argument.
- The exact application candidate `456bb844ef5913dc63ff043684ee0981ed62c6a8` / tree `af9c5f44a14293da78a8ce61b3dd03ce350aeb77`, manifest SHA-256 `35773B28430A9D17C4E13EB53F9E14ADD74760C8315F019EA08B3ABC3DB03D9D`, and applied Migration #13 remain unchanged. One Staging-only Deploy completed and runtime attestation matches. **No Member reset email, Order, Backup, Sentinel, Stop/Resume, or Restore has run in this continuation.**

## Exact compatibility scope

1. Keep every approved `release-candidates/.../emergency/` file and hash unchanged. In Local ignored Stage1 executor only, verify each pinned file hash before use. For each of the six Stop/Resume SQL files, strip only **leading full-line comments** for CLI transport; preserve string literals and the exact parsed ordered `REVOKE`/`GRANT` statement inventory. Verify affected ACL after each command. No new DDL/DML or extra command. The CLI argument is explicitly a deterministic transport form, **not byte-identical to the source file**.
2. For Reconcile on this Staging only, verify the original `reconcile.sql` hash, then use a new Local ignored, SHA-256-sealed SELECT-only compatibility variant/executor. Execute each expected SELECT separately through standard linked InsForge CLI; demand exactly one correctly typed row per expected count/verifier/ACL query, never treat `rows:[]` as success. Repeat exact Project/context and catalog absence checks immediately before Reconcile. Before substituting the one Hold query, require a fresh exact-project read-only `to_regclass('public.payment_workflow_holds') IS NULL`. Record Hold as `NOT_APPLICABLE_TABLE_ABSENT` with catalog absence proof/hash/time, **not** numeric zero and not a PASS for the old pinned query. Exclude this status from numeric zero checks. Preserve every other existing count, verifier and ACL check and fail on missing/ambiguous/nonzero disallowed results. Because separate SELECTs are not one atomic snapshot, compare relevant read-only totals and target identity before/after the sequence and fail on drift. If the Hold table exists or the schema changes, stop; do not switch branches silently.
   This expressly supersedes only Lean Temporary Staging v0.1 §6's `pass exact file bytes/no inline modification` and pinned single-call `run-reconcile.mjs` execution requirements **for this named Staging Stage1 CLI transport**. The original source files and hashes remain retained and checked, not overwritten or reported as successfully executed byte-for-byte.
3. Independent QA must verify the exact package and create fresh initial and Billing gates before any next Staging write. Prior expired QA/Billing artifacts may be retained as evidence but not reused as authorization.
4. After QA PASS and fresh preflight/Billing, continue only the previously approved one Member 01 Order proof and one post-#13 Backup/Sentinel/Stop→Reconcile→Resume/Restore on the same Staging. No duplicate Order, backup, email or Restore on uncertain outcome. No new Migration, app Deploy, account, Catalog, Config, Schedule, Notification or Production action. The Staging-only exception is not automatically authorized for Production.
