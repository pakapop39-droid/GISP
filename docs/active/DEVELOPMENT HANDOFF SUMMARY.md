# GISP — สรุปแอปและแนวทางพัฒนาต่อ

วันที่จัดทำ: 11 กันยายน 2569 (2026-09-11)  
อัปเดต Environment: 13 กันยายน 2569 ตาม ENV2-v0.1  
วัตถุประสงค์: ใช้ส่งต่องานให้เจ้าของระบบ ผู้พัฒนา หรือ AI เริ่มทำงานต่อได้โดยเข้าใจขอบเขตและสถานะเดียวกัน

> เอกสารนี้สรุปจากโค้ดและหลักฐานในโปรเจกต์ ณ วันที่จัดทำ ไม่ได้ตรวจระบบออนไลน์หรือรันทดสอบใหม่ในรอบจัดทำเอกสาร สถานะการเผยแพร่และผลทดสอบด้านล่างเป็นผลที่บันทึกไว้ตามวันที่ของหลักฐาน ต้องตรวจซ้ำก่อนเปลี่ยนระบบจริง

## 1. แอปนี้ทำอะไร

GISP (Global Interior Supply Platform) เป็นเว็บแอปจัดหาและบริหารการสั่งซื้อเฟอร์นิเจอร์และวัสดุตกแต่งจากจีน สำหรับนักออกแบบ ผู้รับเหมา ตัวแทนจำหน่าย และสมาชิกที่ได้รับอนุมัติ โดยเชื่อมงานตั้งแต่เลือกสินค้า จัดโครงการ ขอผลิตตามแบบ เสนอราคา สั่งซื้อ ชำระเงิน ติดตามผลิต ตรวจคุณภาพ ขนส่ง จนถึงเคลมและรับประกัน

ระบบแบ่งผู้ใช้งานหลักเป็น:

- **สมาชิก:** ดูสินค้าและราคาสมาชิก จัดรายการสินค้าในโครงการ แชร์แค็ตตาล็อกให้ลูกค้า และส่งคำขอจัดหา ก่อนเข้าสู่การสั่งซื้อเมื่อเปิด Release ที่รองรับ
- **ทีมงาน GISP:** จัดการสมาชิก สินค้า ผู้ผลิต ราคา ใบเสนอราคา การเงิน การผลิต ขนส่ง และเคลม ตามสิทธิ์ของแต่ละคน
- **เจ้าของระบบ/ผู้บริหาร:** กำหนดสิทธิ์ ตั้งค่าบริษัทและสูตรราคา ดูรายงานและประวัติการทำงาน
- **ลูกค้าของสมาชิก:** เปิดแค็ตตาล็อกผ่านลิงก์ที่สมาชิกแชร์ โดย Customer Browse Catalog ไม่มีราคา

## 5. งานเพิ่มเติมล่าสุด

### 5.1 จัดการพนักงาน

เพิ่มหน้ารายชื่อพนักงาน การค้นหา แสดงกลุ่มงาน/สถานะ และส่งลิงก์ตั้งรหัสผ่านใหม่ผ่านอีเมล InsForge เจ้าของระบบไม่เห็นรหัสผ่านเก่า

หลักฐานวันที่ 11 กันยายนระบุ Build ผ่าน และ Owner/API Tests ผ่าน 23 รายการ ตรวจหน้าเจ้าของระบบทั้งสองเว็บไซต์แล้ว แต่ยังไม่ได้ทดสอบส่งอีเมลจริงหรือเปลี่ยนรหัสผ่านจริงในรอบนั้น

ชุดที่เผยแพร่ใช้ Release B commit `45b7b03` พร้อมไฟล์จัดการพนักงาน 10 ไฟล์ ไม่รวม Image Search ที่อยู่ระหว่างแก้ใน workspace ดังนั้นโค้ดทั้งหมดในเครื่องไม่เท่ากับชุดที่เผยแพร่ล่าสุด

ดู [หลักฐานการเผยแพร่จัดการพนักงาน](../evidence/2026-09-11-staff-management-deployment.md)

### 5.2 Image Search

ฟังก์ชันนี้ค้นหาสินค้าที่คล้ายภาพในแค็ตตาล็อก แตกต่างจาก Slice 13 ซึ่งเป็นการส่งคำขอให้ทีมงานช่วยจัดหา

- ดัชนีภาพหลัก 634 สินค้า ใช้ pgvector ขนาด 1,024 มิติ ค้นด้วย cosine similarity และกรองสิทธิ์ผ่าน `member_catalog`
- แสดงสูงสุด 12 ผลลัพธ์ ไม่ส่ง vector ต้นทุน หรือข้อมูลโรงงานไป browser
- โควตา 30 ครั้งต่อบัญชี/องค์กรต่อวันตามเวลาไทย เว้นอย่างน้อย 2 วินาทีระหว่างคำค้น
- Worker อัปเดตดัชนีตามการเปลี่ยนภาพ มี retry, lease และตรวจ revision ป้องกันผลเก่าเขียนทับ
- ผ่าน Owner UAT รุ่นออนไลน์แล้ว ปิด Slice เฉพาะ Development; ต้องเตรียม Release แยกหากจะเปิด Production
- ความแม่นยำกับรูปถ่ายหน้างานยังควรประเมินตามชุดทดสอบจริง ไม่ใช้ผลค้นจากภาพสินค้าต้นฉบับแทนคุณภาพทุกสถานการณ์
- Migration ตรวจ lifecycle ต้องมี seeded index ก่อน จึงไม่ควรรันทุก migration บนฐานข้อมูลใหม่โดยไม่แยกประเภท

ดู [หลักฐานออนไลน์](../evidence/2026-09-09-image-search-online-preview.md), [แผน Image Search](../IMAGE-SEARCH-IMPLEMENTATION-PLAN.md) และ [ชุดทดสอบภาพจริง](../uat/IMAGE-SEARCH-REAL-PHOTO-TEST.md)

### 5.3 ล้างบัญชีทดสอบ

ขอบเขตที่ได้รับยืนยันคือบัญชีทดสอบอัตโนมัติ 15 บัญชีและข้อมูลที่เกี่ยวข้อง โดยเก็บสมาชิกอีก 4 บัญชีไว้ สำรองข้อมูลแล้ว แต่ฐานข้อมูลไม่อนุญาตให้ดำเนินการตามแผนลบ ผลตรวจหลังทดลองยืนยันว่าข้อมูลยังเหมือนเดิม

งานนี้เหลือ **2 ขั้นตอน**:

1. มีช่องทางสิทธิ์เจ้าของตาราง ทดลองแบบ rollback ให้ผ่าน แล้วลบตามขอบเขตที่ยืนยันไว้
2. ตรวจว่าบัญชีเป้าหมายเหลือ 0 และข้อมูล/ไฟล์ที่ต้องเก็บยังครบ

ห้ามถือว่าร่าง SQL ผ่านการทดสอบแล้ว และไม่ต้องขอให้ผู้ใช้ยืนยันรายการเดิมซ้ำ ข้อจำกัดที่ต้องแก้คือสิทธิ์ในการดำเนินการ ดู [หลักฐานล้างบัญชีทดสอบ](../evidence/2026-09-11-development-test-account-cleanup.md)

### 5.4 PDF Catalog Import

โค้ดและ Migration อยู่ระหว่างพัฒนาบน Local/Development และยังไม่ใช่ฟังก์ชัน Production การตรวจ InsForge แบบอ่านอย่างเดียวเมื่อ 13 กันยายน 2569 ยืนยันว่า Full Backend Branch `pdf-catalog-import-v1` ใต้ `gisp-mvp-development` อยู่สถานะ `ready` และหลักฐาน live ที่ QA ตรวจพบยืนยันว่า migration `20260912122859`, `20260912234654`, `20260913075421` และ `20260913091000` ถูก apply บน branch นี้แล้ว ห้าม re-apply; Runtime/RLS/Config, Worker, ไฟล์ PDF จริง, QA/UAT, merge และ deploy ยังต้องตรวจแยก

ENV2-v0.1 ไม่เพิ่มสิทธิ์ให้เปลี่ยนฐานข้อมูล Deploy merge ลบ branch หรือเปลี่ยน Production ดู [PDF Builder Handoff](../evidence/2026-09-12-pdf-catalog-import-v1-builder-handoff.md)

## 6. กติกาธุรกิจที่ต้องรักษาเมื่อพัฒนาต่อ

รายละเอียดเต็มให้ยึด [Business Master Plan](MVP%20BUSINESS%20MASTER%20PLAN.md) และ [Decision Log](DECISION%20LOG.md)

- สินค้า Standard ที่มีราคาสมาชิกใช้งานอยู่สั่งผ่านรายการโครงการได้; RFQ/Custom Quotation ใช้กับสินค้า Custom
- ราคาสมาชิกก่อน VAT; VAT เริ่มต้น 7% ปรับใน Company Settings และเก็บค่า ณ เวลาสร้างเอกสารไว้ ห้ามทำให้เอกสารเก่าเปลี่ยนตามการตั้งค่าใหม่
- เงินคำนวณด้วย Decimal ปัด Half-up 2 ตำแหน่ง มัดจำ 50% ของยอดรวม VAT ยอดคงเหลือใช้ยอดรวมลบมัดจำ
- โอนได้หลายครั้ง Finance ต้องยืนยันยอดสะสมครบก่อนถือว่าชำระครบ ยอดเกินต้องตรวจ ไม่รับรองอัตโนมัติ ค่าขนส่งจริงแยกภายหลัง
- ออกจากโรงงานได้เมื่อ QC ผ่าน, สินค้า Custom ได้รับสมาชิกอนุมัติ, ลูกค้าชำระยอดคงเหลือครบและ Finance ยืนยัน, ผู้ผลิตได้รับชำระยอดคงเหลือครบ
- Member ต้องไม่เห็นต้นทุน กำไร เงินจ่ายผู้ผลิต หมายเหตุหรือไฟล์ลับ ผ่านหน้าจอ API Export หรือ URL
- เปิดเผยตัวตนผู้ผลิตตามกติกา Showroom Visit และสิทธิ์ของ Member Profile ไม่ใช้เพียงการซ่อนข้อความบนหน้าจอ
- เปลี่ยนสถานะผ่าน Action Endpoint หรือฟังก์ชันฐานข้อมูลที่ตรวจสิทธิ์ ไม่ให้ browser แก้สถานะข้ามขั้นตอน
- ใช้ Permission Guard ร่วมกับ RLS (สิทธิ์ระดับแถวข้อมูล) เพื่อกันข้อมูลข้ามสมาชิก
- สูตรราคาแก้โดย `SUPER_ADMIN`; เอกสารที่ยอมรับ/สั่งซื้อแล้วต้องเก็บ Snapshot ไม่แก้ย้อนหลังตามต้นทุนหรือสูตรใหม่
- อีเมลส่งไม่สำเร็จต้องบันทึกและ retry โดยไม่ย้อนธุรกรรมหลัก

## 8. วิธีเริ่มพัฒนารอบถัดไป

1. อ่าน `AGENTS.md`, เอกสารนี้ และหลักฐานล่าสุดของโมดูลที่จะทำ ตรวจ `git status --short` ก่อนแก้ไข เพราะ workspace มีทั้งไฟล์แก้ค้างและไฟล์ใหม่ของงานก่อนหน้า
2. ระบุชัดว่าจะทำ Development หรือ Production ตาม [Environment Registry](ENVIRONMENT%20REGISTRY.md); Preview/branch เป็น sandbox ชั่วคราวภายใต้ Development และต้องตรวจโครงการที่ CLI ผูกอยู่ก่อนใช้คำสั่งเปลี่ยนฐานข้อมูล/เผยแพร่
3. ติดตั้ง Node.js ตามข้อกำหนดและ dependencies ด้วย `npm install` หากมี `.env.local` อยู่แล้วให้รักษาไว้; ถ้ายังไม่มีจึงคัดลอกจาก `.env.example` แล้วใส่ค่าของ Development
4. รัน `npm run dev` เพื่อเปิดแอปในเครื่อง การตั้งฐานข้อมูลใหม่ต้องตรวจ migration และ fixture ที่ต้องมีล่วงหน้า ไม่ใช้ `migrations up --all` โดยไม่ตรวจชุดไฟล์ใน workspace ปัจจุบัน
5. แก้เฉพาะขอบเขตที่ตกลง อ่าน InsForge skill ที่เกี่ยวข้องก่อนแก้ SDK/Backend และเก็บ migration ที่ตรวจสอบย้อนกลับได้
6. ตรวจคุณภาพตามความเสี่ยงของงาน แล้วให้ผู้ใช้ตรวจหน้าจอ/ขั้นตอนที่เปลี่ยนเมื่อจำเป็น ก่อนเผยแพร่ตามขอบเขตที่อนุมัติ
7. บันทึกผลทดสอบ สิ่งที่ยังไม่ได้ทดสอบ รุ่น/ปลายทางที่เผยแพร่ และจำนวนขั้นตอนที่เหลือในเอกสารหลักฐาน

คำสั่งตรวจคุณภาพที่มีในโปรเจกต์:

```powershell
npm run typecheck
npm run test
npm run build
npm run check
npm run lint
```

`check` รวม typecheck, test และ build แต่ไม่รวม lint ส่วน `test:slice*:branch` และ fixture scripts อาจเขียนข้อมูลทดสอบ ต้องอ่านสคริปต์และตรวจปลายทางก่อนรัน

Secret ใช้ `.env.local` และไฟล์ตั้งค่า CLI; ห้ามใส่ API Key ในโค้ดหรือเอกสาร ห้าม Commit `.env.local`, `.insforge/project.json` หรือไฟล์สำรองที่มีข้อมูลยืนยันตัวตน Browser ใช้เฉพาะ Public URL/Anon Key ส่วน API Key เป็น server-only

## 9. ลำดับงานพัฒนาต่อที่แนะนำ

รายการนี้เป็นแผนส่งต่อ ไม่ใช่หลักฐานว่าเริ่มทำหรือได้รับอนุมัติให้เปิด Release ถัดไปแล้ว

| ลำดับ | งาน | เกณฑ์จบ |
| --- | --- | --- |
| 1 | จัดชุด source ให้ตรงกับรุ่นที่เผยแพร่ และแยก Image Search/Staff Management/เอกสาร | ระบุได้ว่าแต่ละรุ่นมีไฟล์และ migration ใด ไม่มีงานค้างสูญหาย |
| 2 | ตรวจผล Member Pilot และความพร้อมข้อมูลจริง | ตรวจคำขอสมาชิก Shared Catalog, Sourcing, สิทธิ์, Health, Notification และ Audit พร้อมรายการปัญหาที่ต้องแก้ |
| 3 | เตรียม Release C — ธุรกรรมจริง | ซ้อม RFQ → Quotation → Order → Payment/PO พร้อมยอดเงิน เลขเอกสาร ยกเลิก Audit และป้องกันข้อมูลรั่ว ก่อนเปิดใช้งาน |
| 4 | เตรียม Release D และการเปิด Samples/Warranty ตามขอบเขต | ทดสอบผลิต/QC → ขนส่ง/ส่งมอบ → เคลม/รายงาน และตรวจรับแยกตามโมดูล |
| 5 | ตรวจรับและส่งมอบการดูแลระบบ | มี UAT ของ Release ที่เปิดจริง คู่มือ สำรอง/กู้คืน และผู้รับผิดชอบชัดเจน |

งานแยกที่เลือกทำได้ตามเป้าหมาย: ล้างบัญชีทดสอบที่ติดสิทธิ์ และเตรียม Image Search สำหรับ Production โดยต้องกำหนดคุณภาพภาพจริง งบประมาณ โควตา Migration และการดูแล Worker ก่อนเปิด

อย่าเปลี่ยนเพียงค่า Release หรือซ่อน/แสดงเมนูแล้วถือว่าเปิดธุรกรรมครบ ต้องตรวจทั้ง Route/API และ Backend Gate โดยเฉพาะ [แผน Staged Release](STAGED%20PRODUCTION%20RELEASE%20PLAN.md)
