## การเปิดใช้ของเจ้าของระบบ

1. เข้าเว็บจริง → เข้าสู่ระบบด้วยบัญชี Owner เดิม
2. ไป `/admin/settings` กรอกข้อมูลบริษัทผู้ดำเนินงาน GISP: ชื่อที่แสดง ชื่อนิติบุคคล เลขภาษี ที่อยู่ และอีเมลบริษัท ข้อมูลนี้ใช้ในเอกสารการขายของ GISP
3. ตรวจ VAT, สกุลเงิน และเงื่อนไขที่บริษัทใช้จริง ปัจจุบันค่าที่อนุมัติในแผนธุรกิจคือ VAT 7%, THB, มัดจำ/คงเหลือ 50/50 และค่าขนส่งแยก
4. ตรวจ CN01 ที่ `/admin/catalog` สินค้า 88 รายการที่ข้อมูลยังไม่พร้อมต้องคงเป็นฉบับร่าง
5. ที่ `/admin/users` สร้างบัญชีบุคลากรจริงแยกคนละบัญชี เลือกกลุ่มงานได้มากกว่า 1 กลุ่มตามหน้าที่ที่รับผิดชอบ จัดซื้อ การเงิน QC และขนส่ง การมอบหมายต้องอ้างอิงรายชื่อที่ Owner ยืนยัน
6. เมื่อตรวจเปิดสมาชิกแล้ว สมาชิกสมัครและกรอกข้อมูลบริษัทของตนเอง ทีมงานตรวจเอกสารที่ `/admin/members` ก่อนอนุมัติ

ข้อมูลบริษัท GISP และบริษัทสมาชิกเป็นคนละส่วน ห้ามคัดลอกข้อมูลบริษัทหนึ่งไปใช้เป็นอีกบริษัท

## สำรองก่อนเปลี่ยนระบบ

ผู้ดูแลเทคนิคต้องตรวจ project_id ก่อนสั่งงานทุกครั้ง เก็บผลไว้ใน `output` ซึ่งถูกยกเว้นจากการ deploy

```powershell
# ทำในโฟลเดอร์ที่เชื่อม Production และตรวจ project_id แล้วเท่านั้น
npx -y @insforge/cli backups create --name pre-release-YYYYMMDD --wait --json
npx -y @insforge/cli backups list --json
```

ต้องได้สถานะ `completed` จึงเริ่ม migration/deploy บันทึก deployment เดิม ชุด migration ค่า Release Stage และเวลาหยุดรับรายการไว้ด้วย ห้ามแสดง API key หรือ signed download URL ในเอกสาร

## เมื่อเว็บรุ่นใหม่มีปัญหา

1. ระบุปัญหา เวลา URL และบทบาทผู้ใช้ เก็บข้อความผิดพลาดโดยไม่ส่งรหัสผ่านหรือ OTP
2. หากมีความเสี่ยงเขียนข้อมูลผิด ให้ปิดช่องทางสร้างรายการใหม่ก่อน ตรวจว่ามีธุรกรรมเกิดขึ้นหลัง deploy หรือไม่
3. ถ้าเป็นปัญหาเฉพาะหน้าเว็บ ให้ deploy ชุด source ที่ตรวจผ่านก่อนหน้าโดยใช้ Production env เดิม และตรวจว่า schema ยังเข้ากันได้ ห้ามเปลี่ยน Backend URL เป็น Development
4. ถ้าต้องกู้ฐานข้อมูล ให้สำรองสถานะล่าสุดก่อน เปรียบเทียบออเดอร์ การรับเงิน และหลักฐานที่เกิดหลังจุดสำรอง จัดแผนรักษาหรือกระทบยอดข้อมูลกับ Owner
5. คำสั่ง `backups restore` เขียนทับฐานข้อมูลและ Storage ปัจจุบันบน Cloud จึงต้องยืนยัน backup/project ที่แน่นอนและผลกระทบก่อนสั่งกับ Production
6. หลังแก้ ตรวจ login, catalog, ไฟล์ส่วนตัว, สิทธิ์ข้ามบริษัท, ออเดอร์ และงานแจ้งเตือน แล้วบันทึกผลและเหตุการณ์

**ห้าม restore backup เก่าทับธุรกรรมใหม่โดยไม่กระทบยอด** การย้อนเว็บอย่างเดียวไม่ใช่การย้อน schema

## การดูแลหลังเปิด

- Owner กำหนดผู้รับผิดชอบรับแจ้งปัญหาและรายชื่อผู้รับช่วงงานแต่ละฝ่ายก่อนเปิดเต็มรูปแบบ
- ในช่วง 48–72 ชั่วโมงแรก ผู้รับผิดชอบตรวจรายการเข้าใหม่ การส่งอีเมล ยอดรับเงิน และข้อผิดพลาดทุกวัน
- งาน `GISP-Notification-Retry` ทำงานทุก 10 นาทีบน InsForge ใช้ secret เดิม ห้ามสร้าง schedule ซ้ำ
- ตรวจคำร้องที่ตกค้าง/อีเมลล้มเหลวและ audit log ห้ามเผยแพร่ต้นทุน Supplier หรือไฟล์ภายในให้สมาชิกอื่น
- ยังไม่มีการสร้าง automation สำหรับ Codex เฝ้าดูเบื้องหลังจากคู่มือนี้

## เกณฑ์ส่งมอบ

ต้องมีข้อมูลนิติบุคคลจริง รายชื่อผู้รับผิดชอบ สมาชิก Pilot ที่ยืนยันตัวตนได้ และผลรับมอบจาก Owner จึงระบุว่า “พร้อมใช้งานจริงครบวงจร” ได้ ผลทดสอบอัตโนมัติและการ deploy สำเร็จอย่างเดียวไม่ใช่ผลรับมอบ
