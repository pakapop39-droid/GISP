# GISP — แผนทำ Production ให้พร้อมใช้งานจริง

วันที่: 5 กันยายน 2569

สถานะ: จัดทำแผนตามคำขอเจ้าของระบบ ยังไม่ใช่หลักฐานว่าเปิดฟังก์ชันสมาชิกแล้ว

## เป้าหมายและความหมายของคำว่าเสร็จ

สมาชิกที่ได้รับอนุมัติเข้าเว็บ Production เลือกสินค้า จัดโครงการ ขอราคางานสั่งผลิต
สั่งซื้อ ส่งหลักฐานชำระเงิน ติดตามการผลิต/QC/จัดส่ง และแจ้งเคลมได้ตามสิทธิ์
ทีมงานจัดการงานเหล่านั้นได้จริง พร้อมข้อมูลบริษัท สินค้า ราคา เอกสาร อีเมล
และผู้รับผิดชอบการปฏิบัติงานที่ตรวจสอบแล้ว รวมถึงหน้าขายที่เจ้าของระบบอนุมัติ

คำว่า “ครบ” ในแผนนี้หมายถึง MVP Slice 1–11 ไม่รวม Post-MVP หรือการรับประกันว่าจะไม่มีข้อผิดพลาด
การผ่านบน Development ไม่ใช้แทนหลักฐานการพร้อมเปิด Production

## ฐานข้อมูลประกอบแผน

- Current Project Status v6.0: Slice 1–11 ผ่านบน Development; Production เปิดเฉพาะ Release A
- Staged Production Release Plan v1.6 / DEC-049: เปิด B → C → D ตาม Gate
- Production Authenticated UAT วันที่ 5 กันยายน: หน้าและ API จัดการสมาชิกยัง 404;
  ต้องแก้ก่อน Release B; ณ เวลาที่ตรวจยังไม่มี Supplier/Product จริง
- Phase 5: อีเมล Owner และงาน Notification Retry ผ่านแล้ว แต่ต้องตรวจซ้ำเมื่อเปลี่ยนรุ่น
- Security findings เดิมมี 77 Critical ที่เคยยอมรับเฉพาะ Release A;
  ไม่ถือว่าการยอมรับนั้นครอบคลุมฟังก์ชันสมาชิกและธุรกรรมที่เพิ่มใหม่
- Sale Page ได้รับอนุมัติเนื้อหาแล้ว และเตรียมเป็นหน้าแรกใน source แล้ว แต่ยังไม่ได้เผยแพร่
- การตรวจในรอบวางแผนเป็นการทบทวนเอกสาร ไม่ใช่การตรวจฐานข้อมูล Production ใหม่ทั้งหมด

## แผนดำเนินงาน 8 ขั้นตอน

### 1. ตรวจช่องว่างและล็อกรุ่นที่จะนำขึ้น

ตรวจ Production แบบอ่านอย่างเดียว: deployment, schema/migration history, functions,
permissions, storage, auth/email, schedules และ configuration เทียบกับ Development
ตรวจโค้ดที่ยังไม่เผยแพร่และจัดชุดเปลี่ยนแปลงที่ระบุไฟล์/รุ่นได้แน่นอน
ทำรายการช่องว่างจริง แยกสิ่งที่พร้อม สิ่งที่ต้องแก้ และสิ่งที่ต้องใช้ข้อมูลจากเจ้าของระบบ

ผ่านเมื่อ: มีรายการ migration และ frontend/backend dependencies ครบ พร้อม baseline
ที่ตรวจสอบย้อนกลับได้ และขอบเขต Release B/C/D ชัดเจน

### 2. แก้ข้อบกพร่องและซ้อมการนำขึ้น

แก้ Member Requests 404 และการเปิดเส้นทางตาม Release ให้สัมพันธ์ทั้งหน้าเว็บและ API
ตรวจ RLS/สิทธิ์ข้ามบริษัท ไฟล์ส่วนตัว ต้นทุน สูตรราคา และการเปิดเผย Supplier
ซ้อม migration ตามลำดับบนสภาพแวดล้อมแยกที่ใช้ schema/config ใกล้ Production
ใช้ข้อมูลสังเคราะห์; ไม่คัดลอก fixture, account, secret, schedule หรือข้อมูลธุรกิจจาก Development
เข้า Production โดยตรง ตรวจว่าการ hardening เดิมยังอยู่หลังเพิ่ม/แทนที่ฟังก์ชัน

ผ่านเมื่อ: migration rehearsal, integration, leakage tests และการทดสอบตามบทบาทผ่าน
รวมทั้งมีข้อสรุป findings ใหม่; ปัญหาร้ายแรงที่ยังไม่ได้แก้หรือพิจารณาต้องไม่ผ่าน Gate

### 3. เตรียมข้อมูลและทีมงานจริง

เตรียมชุดข้อมูลที่ตรวจทานได้ก่อนนำเข้า: บริษัท/เลขภาษี/ที่อยู่, บัญชีรับเงิน,
รูปแบบและเลขเอกสาร, Supplier/Product/รูป/ตัวเลือก, สูตรราคาและภาษี,
เงื่อนไขขนส่ง/รับประกัน, ผู้รับผิดชอบจัดซื้อ การเงิน QC ขนส่ง และสมาชิก Pilot 3–5 บริษัท
ยืนยันว่าชุด CN01 หรือชุดอื่นเป็นข้อมูลจริงที่เจ้าของระบบอนุญาต ไม่ใช้ข้อมูลทดสอบแทน
จัดเตรียมข้อความเงื่อนไขการใช้บริการ/ความเป็นส่วนตัวให้เจ้าของระบบตรวจและรับรอง

ผ่านเมื่อ: ชุดข้อมูลและสิทธิ์ทีมงานผ่านการตรวจทาน และมีการอนุมัติรายการที่จะนำเข้าจริง
การเลือกสินค้า/ราคา/บัญชีรับเงินเป็นข้อมูลที่ agent ไม่ควรเดา

### 4. เตรียมการสำรองและย้อนกลับ

สร้าง backup ก่อนแต่ละรอบเปลี่ยน Production ตรวจความครบถ้วนและซ้อม restore ในพื้นที่แยก
บันทึก deployment เดิมและ config ที่ต้องรักษา จัดคู่มือ cutover/rollback และเงื่อนไขหยุด
กำหนดช่วงเปลี่ยนระบบและวิธีจัดการธุรกรรมที่อาจเกิดระหว่างการเปลี่ยนรุ่น

ผ่านเมื่อ: มีหลักฐาน backup/restore และย้อนรุ่นเว็บกับฐานข้อมูลได้อย่างสัมพันธ์กัน
ห้าม restore ทับธุรกรรมใหม่โดยไม่มีแผนรักษาหรือกระทบยอดข้อมูล

### 5. เปิดหน้าแรกและสมาชิกกลุ่มแรก — Release B

เผยแพร่ Sale Page เป็นหน้าแรกจริง เพิ่มทางเข้าสู่ระบบและลิงก์สาธิตที่แยกจากธุรกรรมจริง
นำ schema/permissions/frontend ที่จำเป็นสำหรับสมาชิกขึ้นตามชุดที่ตรวจแล้ว
นำเข้าข้อมูลที่อนุมัติ เปิดสมัคร/OTP/อนุมัติสมาชิก/เข้าสู่ระบบ/กู้รหัสผ่าน
เปิด Catalog/Project/Product Schedule/Visit ตามสิทธิ์ ทดสอบด้วย Pilot ที่กำหนด
คงการปิด RFQ/Order/Payment จน Release C ผ่าน Gate

ผ่านเมื่อ: สมาชิกและทีมงานทำงานใน Production ได้จริง อีเมลและไฟล์ทำงานถูกต้อง
ข้อมูลไม่ข้ามบริษัท และเจ้าของระบบรับผล Pilot; แสดงช่วงนี้ว่า “เปิดสมาชิกจำกัดขอบเขต”
ไม่รายงานว่าแอปพร้อมครบวงจร

### 6. เปิดการสั่งซื้อและการเงิน — Release C

นำ RFQ/Quotation/Order/Payment และเอกสารที่เกี่ยวข้องขึ้นตาม migration ที่ซ้อมแล้ว
ตรวจใบเสนอราคาหลายรุ่น การยืนยัน/หมดอายุ/ยกเลิก สเปกและราคา snapshot
ตรวจเงินมัดจำ/ยอดคงเหลือ/ค่าขนส่ง การชำระซ้ำ ยอดเกิน/ขาด เลขเอกสารและ audit
ตรวจการเงินฝั่ง Supplier และสิทธิ์ข้อมูลภายใน พร้อมกระทบยอดรายงานกับเอกสาร

ผ่านเมื่อ: end-to-end และ reconciliation ผ่านในพื้นที่ทดสอบ และ Production smoke ผ่าน
ก่อนเปิดรับธุรกรรมจริง; การโอนเงินจริง/การส่งเอกสารถึงบุคคลอื่นต้องมีคำสั่งเฉพาะ
ไม่ใช้การสร้างยอดชำระปลอมใน Production เพื่อแทนผลทดสอบ

### 7. เปิดงานหลังสั่งซื้อครบวงจร — Release D และ Slice 11

เปิด Production/QC, Shipment/Delivery, Claim, Dashboard/Reports,
Samples และ Partner Warranty ตาม dependency ที่ตรวจแล้ว
ตรวจ QC ไม่ผ่าน → แก้/ตรวจใหม่, dispatch gate ครบ, partial shipment,
ค่าขนส่งจริง, หลักฐานส่งมอบ, เคลมและ warranty snapshot รวมถึงการปกปิดต้นทุนภายใน
จับคู่ทุกความสามารถที่กล่าวใน Sale Page กับระบบและขั้นตอนของทีมงานที่เปิดใช้ได้จริง

ผ่านเมื่อ: สมาชิกกับทีมงานทดสอบครบเส้นทางตั้งแต่เลือกสินค้าไปถึงหลังส่งมอบ
และไม่มีขั้นตอนสำคัญที่จบได้เฉพาะใน Demo

### 8. ตรวจรับ เปิดใช้ และส่งมอบการดูแล

ตรวจ UAT จาก URL จริงบนมือถือและคอมพิวเตอร์ตามบทบาท ตรวจอีเมล งานเบื้องหลัง
ลิงก์เอกสาร การควบคุมสิทธิ์ และข้อผิดพลาดจริงหลัง deploy
จัดคู่มือสมาชิก/ทีมงาน ผู้รับผิดชอบรับแจ้งปัญหา และคู่มือ incident/backup/restore
เสนอแผนเฝ้าดูช่วงเปิดใช้ 48–72 ชั่วโมงพร้อมผู้รับผิดชอบและเกณฑ์แจ้งเตือน
ยังไม่สร้าง automation หรือสัญญาว่าจะติดตามเบื้องหลังจากการเขียนแผนนี้

ผ่านเมื่อ: ผล UAT และข้อบกพร่องมีข้อสรุป ไม่มีปัญหาขัดขวางงานหลัก
เจ้าของระบบรับมอบ ข้อมูลจริงพร้อม และทีมงานรู้วิธีดำเนินงาน/แก้ปัญหา
จึงใช้สถานะ “Production MVP พร้อมใช้งานจริงครบวงจร”

## การดำเนินงานและการอนุมัติ

ทำงานตรวจ แก้โค้ด เตรียมข้อมูล และซ้อมให้พร้อมตรวจทานก่อนถึงจุดอนุมัติ
ไม่ขออนุมัติซ้ำสำหรับงานที่อนุญาตแล้ว: Sale Page ได้รับอนุญาตให้เผยแพร่แล้ว
แต่คำขอวางแผนนี้ยังไม่ใช่คำสั่งให้นำข้อมูลจริงทุกชุดขึ้นหรือเปิดธุรกรรมทุก Release ทันที
ใช้คำอนุมัติในบทสนทนาที่มีอยู่ร่วมกับ Gate ของแต่ละ Release ก่อนเปลี่ยน Production
หากต้องขอการตัดสินใจ ให้รวมคำถามพร้อมผลตรวจและผลกระทบที่ชัดเจน

## วิธีรายงานความคืบหน้า

รายงาน 3 สถานะแยกกันเสมอ: พัฒนาบน Development / เผยแพร่ Production / เปิดใช้จริง

หากการตรวจพบงานเพิ่ม ให้ปรับรายละเอียดและแจ้งผลกระทบ ไม่ลดขอบเขตเพื่อให้ดูเสร็จ
ยังไม่กำหนดวันเสร็จตายตัวจนขั้นตอน 1–2 ให้ข้อมูลเพียงพอและทราบความพร้อมของข้อมูลจริง
